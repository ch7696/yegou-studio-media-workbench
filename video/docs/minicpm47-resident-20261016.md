# MiniCPM-V4.7-1B 三模型常驻优化实测

2026-10-16，WSL Ubuntu26.04独立Docker，RTX5060Ti16GB。

已实现：MiniCPM-V4.7-1B保持热运行，Qwen3-ASR-0.6B与Qwen3-ForcedAligner-0.6B在独立音频服务内加载一次、复用同一进程。音频和视觉仍按单GPU任务队列依次推理。收益来自消除反复加载与停启，不是让三模型同时抢跑。

## 实测

同一8秒有声动漫经实际7877 WebUI提交，完成ASR、逐词对齐、高清帧/联系图视觉分析和四份文档：

| 完整任务 | 耗时 | ASR与对齐 | 服务重启 |
|---|---:|---:|---|
| 常驻后的首轮 | 28.00秒 | 0.58秒 | 无 |
| 下一轮热任务 | 6.74秒 | 约0.6秒 | 无 |

通过容器StartedAt、音频进程started_at和完成计数验证，两个任务间没有重启视觉或重新加载音频模型。两轮ASR对白一致，均生成13个对齐单元，四份主文档均可下载。第一轮仍有额外视觉阶段开销（约26秒），没有充分分解其来源；不能把所有首轮开销均归因于JIT。第二轮热任务耗时不能代表冷启动或全部素材。

此前同一8秒素材完整联调约94秒，其中ASR约19秒、视觉重启约70秒。当前流程不再每个任务停止视觉模型，直接复用已加载的ASR/对齐模型。这个对比是完整用户流程的效果，非单模型推理速度消融。

另一段23.792秒素材在释放/恢复后完成完整任务，用时19.79秒，含此次音频服务初始化约10秒；视觉未重启。约0.5秒采样观察GPU峰值10144MiB。两段8秒热任务观察总占用10552MiB（10.30GiB），仍余约5.6GiB；最终检查：10144 MiB, 16311 MiB, 0 %。显存包含vLLM预留、三模型与其他GPU占用，素材更长或分辨率更高时峰值会变化，未测与ComfyUI同时渲染。

## 落地行为

- `ASR_EXECUTION_MODE=auto`：4.7-1B默认常驻；其他视觉模型保持旧的分阶段释放模式。`sequential`可回退旧模式，`resident`显式指定常驻。
- `vision-audio-resident`只绑定本机127.0.0.1:8003，两音频模型共享一个服务进程；模型仍是原ASR/ForcedAligner版本，音频产物仍为原JSON/SRT/VTT/Markdown格式。
- WebUI默认不勾选任务后释放，API不传release_gpu时也默认保留；CLI默认同样保留。显式释放选项以及页面“释放显存”会停止本项目视觉与常驻音频容器。其他RAGFlow容器未停止或修改。
- 切换较大视觉模型时，auto策略会先停音频服务以留出预算。仅测试了该路由逻辑，没有加载较大模型进行额外性能测试。
- 服务按镜像、模型路径、最大输出、端口和代码指纹决定复用/重建，启动受文件锁保护，音频推理由互斥锁串行化。
- 每个视频在共享的UUID临时目录中交换文件，读取原媒体时保留一份临时副本，产物复制回正常输出目录后删除。上传/复制仍有I/O开销；超时请求的目录保留，避免正在执行的任务失去输入。
- 修复了缓存软链接路径比较造成的视觉容器误重建。比较双方均规范化为真实路径，后续两轮任务验证均复用了原视觉容器。

## 验证

实际WebUI两轮有声任务成功；无音轨视频的WebUI完整流程成功；缺失或非法job_id返回400；损坏媒体返回500后服务仍能处理下一份媒体；手动释放确实停止两个受管容器；恢复成功，约78.95秒（这次恢复包含视觉启动预热，不是热请求耗时）；最后保留三模型正常待命。Python语法、Bash语法、模式路由与git diff空白检查通过。

联调中先修复了一次root生成临时产物导致宿主清理权限失败，以及软链接误判触发的重建。早期失败任务保留为诊断记录，未算入成功性能数据。最终两轮完整任务与释放/恢复、较长素材已验证修复后的路径。

## 使用

打开 http://127.0.0.1:7877 ，选择MiniCPM-V4.7-1B和导演拉片，保持“分析完成后释放显存”不勾选，即可连续上传。需要ComfyUI显存时点击“释放显存”；下次分析会启动模型，首轮仍需等待加载与预热。

1B视觉描述中的动作/景别/方向错误仍需复核；第四份文档仍是待人工或后续模型深化的解释稿。这次优化没有改变这项质量限制。
